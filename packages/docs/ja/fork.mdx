# フォークガイド

このページは `Endymi0n74/Koharu` フォークについて説明します。コード署名なしでローカルビルドをインストールする方法、ランタイムストアの場所、そして 8GB の VRAM を持つコンシューマー GPU（例: RTX 3070）向けの翻訳モデルの選び方です。

## このフォークでの変更点

アップストリームの Koharu に加えて、このフォークは現在以下の機能を追加しています。

- **ダウンロードの整合性検証** — モデルとランタイムパッケージのダウンロードは、ストアに公開される前に想定サイズと SHA-256 に対して検証されます。
- **llama.cpp ログの表示** — GGUF モデルの読み込みに失敗したとき、具体的な llama.cpp/ggml のログ行がエラーに追加されます。
- **読みやすいアクティビティエラー** — 失敗したジョブのメッセージは中央省略記号で切り詰められ、GGUF ファイル名が強調表示され、複数行のログは「Show more」トグルで展開されます。
- **更新 ID** — `tauri.conf.json` はこのフォークのリリースエンドポイントを指し、フォーク自身のアップデーター鍵で署名されます。

## ローカル（非署名）インストール

アップストリームのリリースバイナリは Authenticode 署名されています。ローカル（または Azure 署名シークレットなしのこのフォークの CI）で生成されたビルドは**署名されていません**。そのため、Windows は初回起動時に「発行元不明」の SmartScreen 警告を表示することがあります。これは正常であり、プログラム自体は同じです。

Windows での一般的なローカルインストール構成:

```text
D:\koharu\
├── koharu.exe              # Tauri アプリケーション（CEF ランタイムが隣にあります）
├── koharu-torch.dll        # ネイティブ torch ランタイム
├── uninstall.exe
└── store\                  # ランタイムストア（下記参照）
```

既存のインストールを更新するには、新しくビルドしたファイル一式をインストールディレクトリにコピーしますが、**`store\` と `uninstall.exe` は除外**してください。ストアはモデルを再ダウンロードしないよう維持する必要があります。上書き前に前の実行ファイルのバックアップを取っておきましょう。

フォークのアップデーター鍵が有効になった後、このリポジトリからビルドされたアプリは、フォークの鍵で署名された更新マニフェストのみを受け入れ、このフォークの GitHub リリースを確認します。

## ランタイムストア

ストアは `resource_dir()/store` に構成されます。上記の構成では `D:\koharu\store` です:

```text
store\
├── hugging-face\
│   ├── models\    <owner>--<repo>\snapshots\<commit>\<file>
│   └── datasets\  ...
├── cuda\          # CUDA ランタイムパッケージ
├── llama\         # llama.cpp ランタイム
├── torch\         # libtorch
└── diffusion\     # stable-diffusion.cpp ランタイム
```

Hugging Face のファイルは、リポジトリ・リビジョン・ファイル名を正確に指定して解決されます。ダウンロードはストリーミングされ、リポジトリのメタデータ（LFS ファイルのサイズ + SHA-256）に対して検証されてから公開されます。切り詰められたファイルや破損したファイルは配備されず拒否され、サイズが誤っているファイルは次回起動時に再ダウンロードされます。

ランタイムパッケージは、各ソースが公開するダイジェストに対して検証されます。GitHub のリリースアセット（llama.cpp、diffusion.cpp、libtorch）には SHA-256 ダイジェストが付いており、CUDA ホイールは PyPI のメタデータに対して検証されます。メタデータ API に到達できない場合や、ダイジェストを公開していない ROCm ホイールの場合は、インストールを失敗させるのではなく、転送自体のバイト数チェックに検証を委ねます。

ストアは数十ギガバイトに成長することがあります。削除するとすべてのモデルとランタイムの再ダウンロード（一般的な回線では数時間）が必要になるため、再インストール時にはそのまま残してください。

## 8GB の VRAM 向け翻訳モデルの選び方

Ryzen 7600 / 32GB RAM / RTX 3070（8GB、CUDA、BF16）での実測値です。制約付き JSON スキーマの下での現実的な 8 セグメントの日本語→フランス語プロンプトを使用:

| モデル | 量子化 | サイズ | 生成速度 | VRAM（ピーク、ビジョンなし） |
|---|---|---|---|---|
| gemma-4-E2B-it | Q4_K_XL | 2.4 GB | 約 139 tok/s | 約 3.1 GB |
| **gemma-4-E4B-uncensored** | **Q4_K_P** | **5.0 GB** | **約 80 tok/s** | **約 4.8 GB** |
| Ministral-3-8B | Q4_K_M | 4.8 GB | 約 66 tok/s | 約 6.6 GB |
| gemma-4-12B-it | Q4_K_XL | 6.3 GB | 約 20 tok/s | 約 7.7 GB |

8GB カードでの推奨:

- **既定: `gemma4-e4b-uncensored`（Q4_K_P）** — 非検閲、ビジョン対応（プロジェクター用に約 0.9GB 追加）、8GB に余裕を持って収まり、12B モデルの約 4 倍の速度です。
- **高速なテキスト専用:** `ministral-3-8b-instruct` — 最速の高密度モデルですが、ビジョンはありません。
- **ビジョン付きで非常に高速:** `gemma4-e2b-it` — VRAM 使用量が少なく、翻訳品質は低くなります。
- **8GB では `gemma4-12b-it` は避ける** — ビジョンプロジェクターなしで約 7.7GB に達し、最も遅い選択肢になります。

選択したモデルと量子化は `~/.koharu/config.toml` にあります:

```toml
[pipeline.translation.model]
model = "gemma4-e4b-uncensored"
provider = "local"
quantization = "Q4_K_P"
vision = true
```
